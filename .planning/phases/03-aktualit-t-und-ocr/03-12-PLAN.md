## Phasenziel (Ausschnitt dieses Plans)

Der Nutzer bemerkt nicht, wenn Ereignisse verloren gehen: der Index ist nach einem einzigen nächtlichen Abgleichzyklus wieder korrekt. Das ist das vierte Erfolgskriterium der Phase und die Lehre aus dem Vorgänger, der genau daran still gestorben ist.

<objective>
Der ETag-Abgleich als Container-Pull: der Container liest die Nextcloud-Dateiliste seitenweise, vergleicht sie mit seinem Zustand, reiht Abweichungen über den Requeue-Weg ein und räumt, was es nicht mehr gibt.

Purpose: Ereignisse sind ein Beschleuniger, nie eine Garantie. Ein Massenimport über occ, eine Wiederherstellung aus dem Backup, ein Fehler im Dispatcher, ein deaktivierter Listener: in all diesen Fällen kommt kein Ereignis, und ohne Abgleich bleibt der Index dauerhaft falsch, ohne dass ein Zähler auffiele. Genau diese Klasse hat den Vorgänger unbrauchbar gemacht. Der Abgleich ist reine, idempotente Reparatur, und daraus folgt die einzige bewusste Regelabweichung dieser Phase: sein Cursor liegt in der Container-Datenbank statt im Nextcloud-Job-Argument, weil ein verlorener Cursor eine Wiederholung kostet und nie Arbeit.
Output: reconcile.py, Löschbestimmung und Cursor im Store, Takt und Ruhe-Gate, Modul- und Betriebsdokumentation.
</objective>

Ablauf je Scheibe (Pattern 3 der Phasenrecherche):
  1. Ruhe-Gate prüfen (D-03): queue.stats().scheduled unter der Schwelle.
     Sonst nichts tun und später erneut sehen.
  2. GET /mounts, Mounts der Reihe nach.
  3. GET /files/slice?storage=&root=&after=&limit= liefert eine Seite plus final.
  4. Vergleich gegen die eigene files-Tabelle:
     - file_id unbekannt oder etag abweichend -> Requeue-Liste (kind=content)
     - lokal vorhanden mit storage_id = S und after < file_id <= letzte_id
       (bei final ohne obere Grenze), aber nicht in der Seite -> gelöscht
       -> Requeue als kind=delete
  5. POST /queues/documents/requeue mit den beiden Listen (getrennt je Art).
  6. Cursor in state.db fortschreiben, nächste Scheibe.

Warum die Löschung über die Queue geht statt lokal:
  Es gibt genau einen IndexWriter im Prozess, und der gehört dem Poller. Ein
  zweiter wäre ein Tantivy-Lock-Konflikt. Der Abgleich schreibt deshalb nie in
  den Index; er erzeugt Aufträge, und der Löschzweig aus Plan 03-03
  erledigt sie. Nebenwirkung, die erwünscht ist: der Löschweg existiert genau
  einmal statt zweimal.

Takt (D-02, Pitfall 5):
  Der Takt liegt im Container, nicht in einem Nextcloud-TimedJob. Ein PHP-Job
  könnte den Container nicht wecken, und D-01 verbietet ausdrücklich einen
  neuen Weckkanal. Also: höchstens ein vollständiger Zyklus je
  FINDLING_RECONCILE_MIN_INTERVAL_HOURS (Default 24), bevorzugt in der Stunde
  FINDLING_RECONCILE_HOUR (Default 2, Containerzeit), und nur bei ruhiger Queue.
  Der Grund, warum das Wartungsfenster von Nextcloud nicht reicht, gehört in
  docs/reconcile.md: maintenance_window_start hat den Default 100 und ist damit
  auf einer frisch installierten Instanz aus.

Scheiben-Disziplin, damit der Abgleich auch mittags erträglich ist:
  Seitengröße 500, Pause zwischen den Scheiben, Abbruch der Runde, sobald das
  Ruhe-Gate fällt. Ein Abgleich, der nur nachts erträglich ist, ist ein
  Abgleich, den ein Admin abschaltet.

Neue Tabelle in schema.sql (CREATE TABLE IF NOT EXISTS, damit keine
SCHEMA_VERSION-Anhebung nötig ist):
  reconcile(storage_id INTEGER PRIMARY KEY, after_file_id INTEGER NOT NULL
            DEFAULT 0, started_at INTEGER, finished_at INTEGER)

Neue Umgebungsvariablen (config.py und backend/appinfo/info.xml):
  FINDLING_RECONCILE_ENABLED        default true
  FINDLING_RECONCILE_HOUR           default 2
  FINDLING_RECONCILE_MIN_INTERVAL_HOURS default 24
  FINDLING_RECONCILE_QUIET_MAX      default 100 (scheduled-Zeilen, D-03)
  FINDLING_RECONCILE_SLICE          default 500
