Der Docblock von dirtyFileIds (Z. 694-704, "Read for the answer ... both statements decide themselves") wird auf die neue Lesereihenfolge nachgezogen. 2. Backstop im Container und nicht im PHP-Claim: nur der Container kennt die Bytes (content_hash); der Claim sieht nur retries, und retries wird von requeueAs bewusst genullt (Pitfall 11, Docblock Z. 567-571). Ein Hash-Vergleich ist das einzige Kriterium, das eine kreisende Datei von einer legitim wiederkehrenden (geänderte Bytes) unterscheidet. Schwelle drei wie die Give-up-Regel der Claim-Seite (MAX_DELIVERIES-Analogie). Gezählt werden nur ERFOLGREICHE Übergaben (moved.ok), damit die CR-02-Redelivery (verlorene requeue-Antwort, Docblock von _goes_to_the_ocr_track Z. 2123-2137) nie in den Backstop läuft. Ein echtes OCR-Urteil räumt den Eintrag, damit die Map proportional zu den Dateien ZWISCHEN den Spuren bleibt (Speichergrenze 4-GB-Box) und ein späterer legitimer Neuanlauf bei null beginnt. Prozess-Neustart leert die Map: hingenommen und dokumentiert, die Schleife läuft dann höchstens zwei weitere Übergaben, bevor der Zähler wieder greift; catchup (D-31-02) bietet eine abgeschriebene Datei nach einem Update genau einmal neu an, dann gelten drei neue Chancen zu Recht. Die Anzahl in der warning-Zeile zählt die VERLANGTEN Übergaben (drei: zwei erfolgte plus die verweigerte dritte), und der Wortlaut sagt das ("demanded handovers"), damit die Zahl nicht als "drei erfolgte Übergaben" gelesen wird.
