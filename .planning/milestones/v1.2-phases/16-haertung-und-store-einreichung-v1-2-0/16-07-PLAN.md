**Der Name.** `Version001200Date<JJJJMMTThhmmss>`, und der Datumsteil ist der
Tag, an dem die Datei entsteht. Der Plan traegt `20260922000000` als
Arbeitsnamen in seiner Dateiliste; wenn die Datei an einem anderen Tag entsteht,

**Dateiname und Klassenname muessen zeichengleich sein.** Nextcloud laedt
Migrationen ueber den Dateinamen und baut die gleichnamige Klasse; bei einer
Abweichung wird die Migration still nie ausgefuehrt, ohne Fehler an irgendeiner
Stelle.

**Der Rumpf**, nach den fuenf Regeln der Vorlage:

- Sie sitzt in `postSchemaChange`, weil sie Daten anfasst und keine Tabelle.
- Sie liest `ExAppService::KEY_BACKEND_VERSION` ueber `IAppConfig` und
  **verwirft** den Wert. Sie schreibt `ownVersion()` NICHT hinein: eine Instanz,
  deren Container wirklich eine Minor zurueckliegt, bekaeme damit Einigkeit
  bescheinigt, und das ist die eine Aenderung, die die Zusage leert.
- Ein fehlender Schluessel ist ein `no-op` mit einer Meldung ueber `$output->info`
  und kein Wurf. Nextcloud kann eine Migration nach einem gescheiterten Upgrade
  wiederholen.
- Sie fragt den Container nicht. Sie laeuft im Wartungsmodus, ohne angemeldeten
  Nutzer, und moeglicherweise waehrend AppAPI den Container neu startet.
- Der Klassenkommentar wird fortgeschrieben, nicht kopiert: er sagt, warum es
  diese Migration gibt (der Minor-Sprung 1.1.0 auf 1.2.0), und er behaelt den
  Satz, dass jeder Minor-Sprung eine braucht, solange die Marke so gepflegt wird
