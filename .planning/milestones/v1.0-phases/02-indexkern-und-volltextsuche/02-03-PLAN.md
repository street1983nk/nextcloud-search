<objective>
Die Pull-Queue entsteht auf der Nextcloud-Seite: eine eigene Tabelle, Zeilen-Locks über ein bedingtes UPDATE, vier ExApp-gebundene Endpunkte und ein Rückkanal für alles, was der Container nicht verarbeiten konnte.

Purpose: Das ist die Invariante, an der das offizielle fulltextsearch-Framework gescheitert ist. Niemand pusht Arbeit in den Container, der Container holt sie, wenn er kann. Backpressure entsteht dadurch von selbst, und ein abgestürzter Container staut Arbeit an, statt sie zu verlieren. Der Lock-Timeout ist bewusst kurz, weil die 24 Stunden des Vorbilds nach einem `docker kill` einen ganzen Tag Stillstand bedeuten würden. Der `failed`-Rückkanal im Quittungsaufruf ist neu gegenüber dem Vorbild und trägt IDX-06: ohne ihn müsste die Statusseite der Phase 4 den Container fragen, und das wäre ein zweiter Wahrheitsort.
Output: Migration mit zwei Tabellen, Entität, Mapper mit Zeilensperre und Upsert, zwei Services und ein OCSController mit vier Endpunkten.
</objective>

  findling_queue
    id bigint autoincrement, file_id bigint, storage_id bigint, root_id bigint,
    is_update boolean default false, size bigint null, locked_at datetime null,
    retries smallint default 0
    PrimaryKey(['id'], 'findling_q_id')

    Index(['storage_id','root_id'], 'findling_q_stor')

  Die Spalte heisst is_update, nicht update: update ist in mehreren Dialekten ein
  reservierter Bezeichner. Tabellennamen bleiben unter 27 Zeichen inklusive oc_,
  Indexnamen unter 30.

  findling_file_state  (der Rueckkanal, Datenbasis der Phase-4-Diagnose)
    file_id bigint primary, state string(16), reason string(32) null,
    updated_at datetime
    Index(['state'])

Fuenf begruendete Abweichungen vom Vorbild context_chat:
  1. Lock-Timeout 15 Minuten statt 24 Stunden (sonst wartet der Batch nach einem
     docker kill einen Tag; mit OCR steigt der Wert in Phase 3)
  2. Zusaetzlicher Unlock-Endpunkt fuer den SIGTERM-Pfad
  3. Deduplizierung ueber den Unique-Index plus Upsert statt Select-vor-Insert
     (der Vorher-Select ist ein Race zwischen parallelen Crawl-Jobs)
  4. Batchgrenze zusaetzlich in Bytes, dafuer die Spalte size
  5. Spalte retries, Abbruch bei 3 als failed(repeatedly_stuck)

Zeilensperre (RESEARCH "Frage 2", Abschnitt "Das verifizierte Original"):
  Kandidaten waehlen mit locked_at IS NULL OR locked_at <= now - LOCK_TIMEOUT,
  sortiert nach id ASC, is_update ASC. Danach je Zeile ein UPDATE mit derselben
  Bedingung im WHERE; nur executeStatement() >= 1 gewinnt die Zeile. Kein
  SELECT FOR UPDATE, keine dialektspezifische Klausel.

Endpunkte, alle #[ExAppRequired] (RESEARCH "Frage 2", Endpunkttabelle):
  GET    /queues/documents?n=32&max_bytes=67108864  -> {files: {queueId: Source}}
  DELETE /queues/documents  {files: [queueId], failed: [{queueId, reason}]}
  POST   /queues/documents/unlock  {ids: [queueId]}
  GET    /queues/documents/stats   -> {scheduled, running, failed}

  n ist auf 256 gedeckelt. Die failed-Liste im DELETE ist der Rueckkanal: der
  Container sagt beim Quittieren, welche Dateien er nicht verarbeiten konnte und
  warum, und die PHP-Seite schreibt das nach findling_file_state.

Das Source-Objekt (Metadaten, kein Inhalt):

  {"files": {"8123": {"fileId": 4711, "storageId": 3, "rootId": 12,
             "path": "Documents/vertrag.pdf", "title": "vertrag.pdf",
             "mime": "application/pdf", "size": 184320, "mtime": 1755200000,
             "etag": "a1b2c3d4", "userIds": ["alice","bob"],
             "fetchAs": "alice", "isUpdate": false}}}

  Der Schluessel ist die Queue-Zeilen-ID, weil genau die beim Quittieren
  zurueckgeht. content fehlt bewusst: Metadaten und Bytes reisen getrennt.
  userIds ist die ACL-Nutzlast, fetchAs der Nutzer, in dessen Kontext die Bytes
  geholt werden. Wer lesen darf, um zu indexieren, und wer finden darf, sind zwei
  verschiedene Fragen und bleiben zwei Felder. etag ist in Phase 2 ohne Funktion
  und gehoert jetzt ins Protokoll, damit Phase 3 nichts umbaut.

Wer sieht diese Datei (RESEARCH "Frage 3", Abschnitt "Die Quelle"):
  IUserMountCache::getMountsForFileId($fileId), daraus ->getUser()->getUID().
  Bewusst die EINFACHE Variante, je Datei gefragt. Die Optimierung ueber
  getMountsForStorageId plus Pfadpraefix spart bei 100k Dateien rund 200.000
  Abfragen, baut aber die Praefixlogik von UserMountCache nach; ein Fehler darin
  erzeugt einen systematisch zu weiten Vorfilter. Im Erstindex dominiert ohnehin
  der Byteabruf jeder Datei ueber HTTP um Groessenordnungen. Die Optimierung
  gehoert hinter eine Messung in Phase 5, zusammen mit dem Paritaetstest, der
  dort ohnehin geplant ist. Diese Entscheidung gehoert als Kommentar in den Code,
  damit sie nicht als Versehen gelesen wird.
  IShareManager::getAccessList scheidet aus: braucht ein Node, arbeitet rekursiv
  und kennt Team Folders und externe Mounts nicht.

Fehler- und Rueckstau-Semantik (RESEARCH "Frage 2", gleichnamige Tabelle):
  Gateway 404 -> skipped(gone), quittieren, Zeile loeschen
  Gateway 5xx oder Timeout -> NICHT quittieren, Batch abbrechen, Cooldown
  Extraktion wirft oder laeuft in den Timeout -> failed(reason), quittieren
  SIGTERM -> offene IDs per unlock freigeben
